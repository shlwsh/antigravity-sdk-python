# 03 工具机制 (Tools)

在 Google Antigravity SDK 中，**工具（Tools）**是 Agent 扩展其功能、与外部系统交互的核心媒介。工具可以是普通的 Python 同步/异步函数，或者来自外部 MCP 服务器的外部接口。

---

## 🛠️ Python 工具基本定义与注册

你可以直接将任何标准的 Python 函数注册为工具。SDK 依靠函数的 **Docstring（文档字符串）** 和 **类型注解（Type Hints）** 自动生成 JSON Schema，以便让 Gemini 模型理解其功能和参数。

### 示例：定义与注册

```python
from google.antigravity import Agent, LocalAgentConfig

def get_weather_forecast(city: str, days: int = 3) -> str:
    """获取指定城市未来几天的天气预报。

    Args:
        city: 目标城市名称，如 "北京", "Tokyo"。
        days: 预报天数（默认3天）。

    Returns:
        一段天气状况描述文本。
    """
    return f"{city}未来 {days} 天内大部分时间多云，气温适宜。"

# 通过 LocalAgentConfig.tools 列表注册工具
config = LocalAgentConfig(
    tools=[get_weather_forecast]
)
```

> [!TIP]
> **编写高质量 Docstring 的重要性**：
> 模型的工具调用完全依赖于对函数 Docstring 和参数类型提示的阅读。务必提供清晰的函数描述、参数解释和准确的类型标注。

---

## 🧵 同步工具的异步隔离

由于本 SDK 是完全基于 `asyncio` 的异步框架，如果在主线程直接执行耗时的同步代码（例如使用 `requests` 或进行大量本地 IO），会导致整个主事件循环（Event Loop）卡死，甚至使得 WebSocket 连接超时断开。

为了保证性能，SDK 的 `ToolRunner` 具备**自动检测与线程池托管能力**：
- 当模型触发工具调用时，`ToolRunner` 会检测该工具是 `async def` 还是 `def`。
- 如果是同步函数（`def`），SDK 会自动将其提交到**独立的系统工作线程池（Thread Pool）**中后台异步运行。
- 如果是异步函数（`async def`），则直接在当前主事件循环的协程中调度。

这使得开发者可以无缝编写同步或异步工具，无需手动进行线程封装。

## 💾 有状态工具：`ToolContext`

有时，工具需要具有“状态”，即在同一个会话的多个回合之间共享或记忆某些数据。例如：
- **分页查询**：保存当前页面的 cursor/token。
- **中间计算结果**：暂存临时数值。

当工具函数的参数列表里包含名为 `ctx` 且类型提示为 `ToolContext` 的参数时，SDK 的 `ToolRunner` 会在执行时**自动注入**当前的 `ToolContext` 实例。

### 示例：有状态工具（计数器）

```python
from google.antigravity import Agent, LocalAgentConfig, ToolContext

def record_activity(activity_name: str, duration_minutes: int, ctx: ToolContext) -> str:
    """记录某项活动的持续时间，并累计该活动的总时间。

    Args:
        activity_name: 活动名称（如 "reading", "coding"）。
        duration_minutes: 本次活动花费分钟数。
        ctx: 工具上下文（自动注入）。
    """
    # 1. 尝试从 ToolContext 状态中获取当前的计数器字典
    # 状态数据在当前 Conversation 生命周期内持久存在
    activity_log = ctx.get_state("activity_log", {})
    
    # 2. 更新并存储新状态
    if activity_name not in activity_log:
        activity_log[activity_name] = 0
    activity_log[activity_name] += duration_minutes
    ctx.set_state("activity_log", activity_log)
    
    total = activity_log[activity_name]
    return f"已记录 {activity_name} {duration_minutes} 分钟。当前累计总时间：{total} 分钟。"
```

### ⚠️ 状态共享的物理隔离限制

SDK 中存在两个独立的上下文状态系统，它们**物理隔离且不共享状态**：
1. **`ToolContext`**：供工具使用的上下文（`get_state` / `set_state`）。它的生命周期是会话级的。
2. **`HookContext`**：供钩子生命周期拦截器使用的上下文（`SessionContext` / `TurnContext` / `OperationContext`）。它的生命周期常常是 Turn 级或操作级的。

> [!CAUTION]
> 工具**无法**直接读取 Hook 写入 `HookContext` 的数据；Hook 也**无法**直接读取工具写入 `ToolContext` 的状态。如果两边确实需要跨系统通信，必须通过第三方数据库、内存单例或公共存储进行。

## 🚫 限制工具调用的两种机制：禁用 vs 拒绝

SDK 提供了两种限制工具访问的手段，它们作用在不同的阶段，有着不同的 Token 成本和适应场景：

| 特性 / 维度 | 禁用工具 (Config-level Disabling) | 拒绝工具 (Policy-level Denying) |
| :--- | :--- | :--- |
| **生效阶段** | 静态配置期（建立连接前） | 动态运行期（模型发起调用时） |
| **核心配置项** | `CapabilitiesConfig.disabled_tools` | `policy.deny("tool_name")` |
| **LLM 是否可见** | **不可见**（模型根本不知道该工具存在） | **可见**（模型认为工具可用并会尝试调用） |
| **Token 成本** | **无额外开销**，甚至因为模型上下文减小而节省 Token | **有损开销**，模型需要输出调用请求，并在收到拒绝后可能进行重试 |
| **主要优点** | 节省 Token，从源头上杜绝模型胡乱调用的可能 | 支持基于参数或上下文的**条件性拦截**；模型能收到具体拒绝理由，并进行动态调整（如换一种方式重试） |
| **适用场景** | Agent 永远不需要此项能力（如只读 Agent 禁用 `run_command`） | 基于入参安全的拦截（如限制 `run_command` 里的危险字符 `rm`） |

### 禁用工具的配置示例

```python
from google.antigravity.types import CapabilitiesConfig, BuiltinTools

config = LocalAgentConfig(
    capabilities=CapabilitiesConfig(
        # 显式仅启用只读的内置工具，写工具（如 edit_file）将被彻底从 LLM 上下文中抹除
        enabled_tools=BuiltinTools.read_only(),
    )
)
```

### 拒绝/拦截工具的策略示例

```python
from google.antigravity.hooks import policy

policies = [
    # 允许所有工具，但如果是 run_command 且包含 "rm" 则运行时拒绝它
    policy.deny(
        "run_command",
        when=lambda args: "rm" in args.get("CommandLine", ""),
        name="block-destructive-commands"
    ),
    policy.allow_all()
]
```
