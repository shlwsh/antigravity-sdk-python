# 06 背景触发器 (Triggers)

**触发器 (Triggers)** 是与 Agent 会话并行的、长寿命的异步背景任务。它们用于监测**外部事件**（例如定时任务、文件修改、Webhook 请求、外部消息队列等），并在事件发生时主动将通知消息推送给 Agent，从而唤醒 Agent 执行特定任务。

---

## 🆚 Triggers 与 Hooks 的职责对比

虽然 Triggers 和 Hooks 都能对 Agent 产生影响，但它们的设计初衷与作用模式有着本质区别：

| 特性维度 | 生命周期拦截器 (Hooks) | 背景触发器 (Triggers) |
| :--- | :--- | :--- |
| **生命周期** | 单次交互的特定派发点（极短） | 整个 Agent 会话周期（伴随始终） |
| **执行模式** | 内联同步、阻塞主控制流 | 背景异步、多任务并行（独立协程） |
| **核心目的** | 拦截并干预 Agent 自身的生命周期事件 | 监听外部世界的变化并唤醒 Agent |
| **控制流影响** | 可以**阻止、修改或篡改**执行数据 | **无法干预**正在运行的代码，只能发送新消息 |
| **典型案例** | 拦截敏感工具调用并进行安全过滤 | 每隔 5 分钟自动执行一次健康检查 |

---

## 🎛️ `TriggerContext` 与通知发送

每个被激活的触发器在启动时都会被自动注入一个 `TriggerContext` 实例。

该实例提供唯一的通信接口：`send(content: str)`。调用此接口后，SDK 会将消息打包发送给底层 Local Harness。Harness 收到该背景消息后，会在 Agent 空闲时以一个“被动回合”将其作为提示词提交给模型。

---

## 🛠️ 定制触发器装饰器 `@triggers.trigger`

你可以使用 `@triggers.trigger` 装饰器定义一个自定义触发器。装饰器会在启动前严格校验函数签名：
1. 必须是异步函数（`async def`）。
2. 必须接受且仅接受一个参数（`TriggerContext`）。

### 示例

```python
import asyncio
from google.antigravity.triggers import triggers

@triggers.trigger
async def custom_hourly_check(ctx: triggers.TriggerContext) -> None:
    """每小时触发一次的外部系统巡检。"""
    while True:
        await asyncio.sleep(3600)
        # 执行某种外部 API 轮询...
        has_alert = check_external_system()
        if has_alert:
            # 唤醒 Agent 介入处理
            await ctx.send("警报：发现系统异常，请立即运行检查脚本。")
```

## 📦 内置触发器工厂助手 (Helper Factories)

SDK 在 `helpers` 模块中预置了两个最常用的触发器工厂方法：

### 1. 周期性定时触发器：`every(interval_seconds, callback)`
创建一个每隔 `interval_seconds` 秒执行一次 `callback` 的触发器。
```python
from google.antigravity.triggers import helpers

async def check_status(ctx):
    # 唤醒 Agent
    await ctx.send("请更新一次仪表盘数据")

# 每 300 秒（5分钟）调用一次
timer_trigger = helpers.every(300, check_status)
```

### 2. 文件变更监听器：`on_file_change(path, callback)`
基于操作系统的事件机制，高效监听指定文件或目录的变更（新增、修改、删除）。
> [!NOTE]
> **第三方库依赖**：
> 文件监控触发器依赖于第三方库 `watchfiles`。为了避免不需要该功能的项目产生冗余依赖，SDK 采用了**延迟导入（Lazy Import）**机制。只有当你在代码中实际调用 `on_file_change` 时，才会去导入 `watchfiles`。如果未安装，会抛出友好的错误提示：`ImportError: watchfiles is required...`。

```python
from google.antigravity.triggers import helpers
from google.antigravity.types import FileChangeKind

async def handle_file_event(ctx, changes):
    for change in changes:
        if change.kind == FileChangeKind.MODIFIED:
            await ctx.send(f"检测到配置文件修改: {change.path}，请加载最新配置。")

file_trigger = helpers.on_file_change("/path/to/watch/config.json", handle_file_event)
```

## 🧬 触发器生命周期管理 (`TriggerRunner`)

当你在外层配置了 triggers 列表并启动 Agent 时，SDK 内部的 `TriggerRunner` 将接管它们的生命周期：
1. **任务并行化 (Start)**：启动时，`TriggerRunner` 为每一个触发器在主事件循环中创建一个独立的 `asyncio.Task`。
2. **安全隔离性 (Isolation)**：若某个触发器在执行过程中发生了未捕获的异常崩溃，`TriggerRunner` 会捕获并记录日志，但**绝对不会破坏 Agent 的主会话**，也不会影响其他背景触发器的独立运行。不过，崩溃的触发器目前**不支持自动重启**。
3. **优雅关闭 (Stop)**：当 Agent 关闭会话（退出 `async with` 块）时，`TriggerRunner` 会自动向所有触发器发送 Task 取消信号，并确保相关系统资源（如文件描述符句柄、网络套接字）得到优雅释放。

## 💻 完整的触发器应用示例

下面的代码演示了如何在 Agent 会话中注册一个简单的周期性触发器：

```python
import asyncio
from google.antigravity import Agent, LocalAgentConfig
from google.antigravity.triggers import helpers
from google.antigravity.utils.interactive import run_interactive_loop

# 触发器的业务回调函数
async def check_alerts(ctx) -> None:
    # 模拟从外部警报中心拉取数据
    has_event = True  # 假设检测到了告警
    if has_event:
        await ctx.send("系统检测到数据库负载过高，请立即审查数据库进程列表。")

async def main() -> None:
    # 1. 创建定时触发器：每隔 10 秒唤醒一次
    alert_trigger = helpers.every(10, check_alerts)

    # 2. 组装配置
    # 注意：需要增加安全策略以放行相关的内置命令（如运行查看进程的 shell 命令）
    from google.antigravity.hooks import policy
    policies = [
        policy.deny_all(),
        # 允许 Agent 执行查看系统命令
        policy.allow("run_command")
    ]

    config = LocalAgentConfig(
        triggers=[alert_trigger],
        policies=policies
    )

    # 3. 启动 Agent 并进入交互式命令行循环
    # 此时，即使你在控制台不输入任何内容，定时触发器也会在后台运行，并在 10 秒后往会话里灌入通知
    async with Agent(config) as my_agent:
        print("=== 触发器运行中 (每 10 秒检查告警) ===")
        # 启动 CLI 交互式界面，背景任务将被自动托管调度
        await run_interactive_loop(my_agent)

if __name__ == "__main__":
    asyncio.run(main())
```
