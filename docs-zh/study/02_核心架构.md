# 02 核心架构

Google Antigravity SDK 采用了清晰的三层架构设计，实现了高层声明式 API、中层会话状态管理和底层 network 传输适配器的解耦。

---

## 🏛️ 三层架构体系

SDK 内部共分为以下三层，层与层之间职责单一、边界清晰：

```
┌──────────────────────────────────────────────┐
│  Layer 1 — 声明式入口层 (Agent)               │
│  管理生命周期、能力集、Hooks、触发器、MCP 桥接   │
│                                              │
│  ┌────────────────────────────────────────┐  │
│  │  Layer 2 — 会话状态层 (Conversation)   │  │
│  │  管理历史 Step、当前 Turn、上下文压缩、Token  │  │
│  │                                        │  │
│  │  ┌──────────────────────────────────┐  │  │
│  │  │  Layer 3 — 适配器/传输层 (Connection)│  │  │
│  │  │  管理二进制运行时进程、协议收发、心跳  │  │  │
│  │  └──────────────────────────────────┘  │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
```

### 1. Layer 1 — 声明式入口层 (`Agent`)
* **核心类**：`Agent`
* **职责**：
  - 作为用户最常用的统一入口。
  - 管理 Agent 配置（如模型选择、系统提示词）。
  - 管理 Python 本地工具和 MCP 远程服务器注册。
  - 管理 Hook 生命周期拦截器和安全策略（Policies）注册。
  - 管理背景触发器任务（Triggers）。
  - 控制底层的启动（`__aenter__`）和清理关闭（`__aexit__`）。
* **心智模型**：这是**静态配置的容器**。它规定了 Agent 可以使用什么工具、遵循什么安全限制。

### 2. Layer 2 — 会话状态层 (`Conversation`)
* **核心类**：`Conversation`
* **职责**：
  - 维护会话的历史轨迹（Trajectory），即一组按顺序发生的 `Step` 列表。
  - 追踪多回合（Turns）边界，以便在发送新 prompt 时能够附带之前的记忆。
  - 处理上下文压缩（Compaction）：当 token 数量超过设定阈值时，自动记录压缩点。
  - 统计会话总 Token 使用量。
* **心智模型**：这是**动态状态的容器**。它记录了 Agent 在本次对话中实际已经执行了哪些操作、输出了什么文本。

### 3. Layer 3 — 适配器/传输层 (`Connection` & `ConnectionStrategy`)
* **核心类**：`Connection` (抽象基类)、`LocalConnection` (本地适配器)
* **职责**：
  - 处理具体的进程管理。例如在本地模式下，负责发现、启动和杀死底层的 Go 语言运行时（Local Harness）二进制文件。
  - 处理网络协议（Wire Protocol）。建立 WebSocket 连接，并将 Python 端的数据与 Local Harness 端的 Protobuf/JSON 数据进行双向转换。
  - 维护连接心跳、断线重连、以及取消当前回合（Cancel）的传输控制。
* **心智模型**：这是**网络和进程的管道**。它只负责在 Python 代码和底层的 Go 执行引擎之间安全、高效地搬运字节。

## 🔍 核心类职责划分与设计动机

为什么不直接把所有东西放在一个 `Agent` 类里？这种拆分带来了以下好处：

| 关注点 | 归属者 (Owner) | 归属动机 |
| :--- | :--- | :--- |
| **Config, Hooks, Policies, Tools** | `Agent` | 这些是**声明式配置**（Declarative Setup），定义了 Agent “可以”做什么，与特定的一段对话历史无关。 |
| **History, Turns, Usage, Compaction** | `Conversation` | 这些是**会话状态**（Session State），在互动的过程中不断累积，随时可以清空重来或序列化存档。 |
| **Wire Protocol, Process Lifecycle** | `Connection` | 这是**传输管线**（Transport Plumbing），涉及多线程、进程生命周期、WebSocket 网络状态，需要对上层彻底屏蔽。 |

### 支持“一个配置，多段对话”
这种解耦允许更高级的使用场景。例如，你可以创建一个 `Agent` 实例（包含昂贵的 MCP 服务器连接和工具检测过程），然后通过它启动多个独立的 `Conversation` 会话，而各会话之间互不干扰，从而显著提高并发效率。

```python
# 伪代码：在同一个 Agent 实例中运行两个独立会话
async with Agent(config) as agent:
    strategy = agent._strategy # 获取连接策略
    async with Conversation.create(strategy) as conv1:
        await conv1.chat("会话 1 的内容...")
    
    async with Conversation.create(strategy) as conv2:
        await conv2.chat("会话 2 的内容...")
```

## 📡 底层 LocalConnection 的网络流转

当你在 Python 端调用 `await agent.chat("List files")` 时，内部究竟发生了什么？

```
 Python SDK                                             Local Harness (Go Binary)
 ┌──────────┐                                                ┌─────────────┐
 │  Agent   │                                                │             │
 └────┬─────┘                                                │             │
      │ chat(prompt)                                         │             │
      ▼                                                      │             │
 ┌──────────┐                                                │             │
 │ Convers- │                                                │             │
 │ ation    │                                                │             │
 └────┬─────┘                                                │             │
      │ send_event / WebSocket                               │             │
      ▼                                                      │             │
 ┌──────────┐ ─── JSON Protobuf: InputEvent("List files") ──►│ 接收事件，   │
 │ LocalCon-│                                                │ 驱动 LLM    │
 │ nection  │                                                │ 思考决策    │
 │          │◄── JSON Protobuf: StepUpdate(TEXT/TOOL_CALL) ──│             │
 └────┬─────┘                                                └──────┬──────┘
      │                                                             │
      │  如果 StepUpdate 为 TOOL_CALL:                             │
      ├──► (1) 检查安全策略 (Policies/Hooks)                         │
      ├──► (2) 若允许，在本地执行该 Python 函数/MCP 工具             │
      └──► (3) 通过 WebSocket 发回 ToolResult ──────────────────────┘
```

1. **事件提交**：`Conversation` 捕获用户 prompt 并将其包装为 `InputEvent`，通过 WebSocket 发送给底层 Local Harness。
2. **状态驱动**：Local Harness 接收到输入后，调用 Gemini 接口进行决策。
3. **分步推送**：运行时在后台以 `StepUpdate` 的形式实时推送执行细节（文本、工具调用等）。
4. **工具拦截与执行**：
   - 如果收到工具调用（`TOOL_CALL`），`LocalConnection` 会将其拦截。
   - 调用注册在 `Agent` 中的安全钩子（`PreToolCallDecideHook`）。
   - 如果安全策略通过，由 Python SDK 侧的 `ToolRunner` 派发执行，并将 `ToolResult` 序列化为 `OutputEvent` 发送给 Go Harness。
5. **结束回合**：当 LLM 决定输出完成，会推送一个 `FINISH` 类型的 Step，本次 `chat` 调用结束，并生成最终的 `ChatResponse` 对象。

## ⚙️ Local Harness 二进制是什么？

**Harness**（本仓库中具体指 **`localharness`**）是一个用 **Go 语言编写、预编译好的可执行文件**，是 Antigravity Agent 在本地模式下的**真正运行时（Runtime）**。Python 包 `google-antigravity` 主要是**配置、协议适配、工具执行与安全拦截**；与 Gemini 的多轮推理、内置文件/命令工具在 Harness 侧的执行编排，由该二进制完成。

可以把它类比为：

| 类比 | Harness 的角色 |
| :--- | :--- |
| 数据库 | Python SDK ≈ 客户端驱动；Harness ≈ 数据库引擎进程 |
| 游戏引擎 | Python ≈ 脚本/UI；Harness ≈ 核心循环与渲染 |
| 浏览器 | Python ≈ 扩展/自动化；Harness ≈ 真正访问模型与执行内置能力 |

### 它从哪里来？

- **文件名**：`localharness`（Windows 为 `localharness.exe`）
- **安装位置**（`pip install google-antigravity` 后）：  
  `site-packages/google/antigravity/bin/localharness`（约 120MB 级，随平台 wheel 不同）
- **本 Git 仓库**：通常**只有** Python 源码和 `localharness_pb2.py`（协议生成代码），**不含** Go 可执行文件；必须从 PyPI wheel 获得二进制
- **查找顺序**（`LocalConnectionStrategy`）：环境变量 `ANTIGRAVITY_HARNESS_PATH` → 包内 `bin/localharness` → 系统 `PATH`

### Python 与 Harness 如何分工？

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        你写的应用 / examples                             │
└─────────────────────────────────┬───────────────────────────────────────┘
                                  │ Agent / Conversation API
┌─────────────────────────────────▼───────────────────────────────────────┐
│  Python SDK（本仓库 google/antigravity）                                 │
│  · LocalAgentConfig、Policies、Hooks、MCP、ToolRunner                    │
│  · 启动/关闭子进程、WebSocket 客户端、Protobuf↔Python 类型转换            │
│  · 执行「宿主侧」工具：自定义 Python 函数、MCP 工具                       │
│  · 工具调用前 Policy / Hook 审批                                         │
└─────────────────────────────────┬───────────────────────────────────────┘
          stdin/stdout 握手          │  WebSocket (JSON 序列化的 Protobuf)
          + 子进程生命周期            │
┌─────────────────────────────────▼───────────────────────────────────────┐
│  localharness（Go 二进制）                                               │
│  · 调用 Gemini / Vertex API（Agentic 循环：想→调工具→再想）                 │
│  · 内置工具：list_directory、view_file、edit_file、run_command 等         │
│  · 维护对话轨迹、上下文压缩、子 Agent、生图、向用户提问等                   │
│  · 需要确认时发 ToolConfirmation；需要宿主工具时发 ToolCall 给 Python     │
└─────────────────────────────────────────────────────────────────────────┘
```

**为什么在 Go 里做这些？** 官方把高性能、与模型 API 紧耦合的 Agent 循环放在独立运行时中；Python 层保持可扩展（工具、策略、MCP），并避免在纯 Python 里重复实现整套 Agent 引擎。

### 启动时发生了什么？（两阶段握手）

`async with Agent(config)` 进入时，`LocalConnectionStrategy.__aenter__` 会：

**阶段 1 — 进程握手（stdin/stdout）**

1. `subprocess.Popen([localharness])` 拉起子进程  
2. 向 **stdin** 写入：`4 字节长度` + `InputConfig`（Protobuf），含会话存储目录、`ClientInfo`（python 版本等）  
3. 从 **stdout** 读取：`4 字节长度` + `OutputConfig`，得到 **WebSocket 端口** 和连接用 **api_key**  
4. 后台线程持续读取 **stderr**，避免管道塞满导致 Harness 卡死  

**阶段 2 — WebSocket 会话**

1. 连接 `ws://localhost:{port}/`，请求头带 `x-goog-api-key`  
2. 发送 `InitializeConversationEvent`，内含 `HarnessConfig`：  
   - `gemini_config`（模型名、API Key、Vertex、thinking_level）  
   - `system_instructions`、`workspaces`  
   - `harness_side_tools`（各内置工具 enable/disable）  
   - 自定义工具的 JSON Schema（`tools` 列表）  
   - `cascade_id`（会话恢复）、`compaction_threshold` 等  
3. 之后所有对话都走 WebSocket 上的 `InputEvent` / `OutputEvent`

关闭 Agent 时会断开 WebSocket 并终止子进程。

### 运行时消息类型（协议概览）

Python 与 Harness 通过 **Protobuf 定义、JSON 序列化** 通信（见 `localharness_pb2.py`）。常见消息：

| 方向 | 消息 | 含义 |
| :--- | :--- | :--- |
| Python → Harness | `InputEvent`（`user_input` / `complex_user_input`） | 用户新一轮 prompt |
| Python → Harness | `InputEvent`（`tool_response`） | 自定义/MCP 工具执行结果 |
| Python → Harness | `InputEvent`（`tool_confirmation`） | 内置工具是否允许执行（Policy 结果） |
| Python → Harness | `InputEvent`（`question_response`） | 用户对 `ask_question` 的回答 |
| Python → Harness | `InputEvent`（`halt_request`） | 取消当前回合 |
| Harness → Python | `OutputEvent` / `StepUpdate` | 流式步骤：模型文本、工具请求、错误、完成 |
| Harness → Python | `ToolCall` | 要求在 Python 侧执行某 MCP/自定义工具 |

Python 把 `StepUpdate` 转成 `types.Step`，供 `Conversation` 累积历史和流式 `ChatResponse`。

### 两类工具：谁执行？

| 类型 | 例子 | 执行方 |
| :--- | :--- | :--- |
| **Harness 内置工具** | `list_directory`、`run_command`、`edit_file` | Go 进程在本机执行（先经 Python Policy 确认） |
| **宿主工具** | 你注册的 Python 函数、MCP 工具 | Harness 发 `ToolCall` → Python `ToolRunner` 执行 → 回传 `tool_response` |

因此：**没有 Harness 二进制，Python SDK 无法单独完成一次 `chat()`**——它没有内嵌 Gemini Agent 循环的实现。

### 和「Antigravity IDE」的关系

本仓库是 **Antigravity 体系的 Python SDK**，Local Harness 与 Google Antigravity 产品共用同一类运行时思想；你 `pip install` 得到的是**面向 SDK 集成的本地 Harness**，不必单独安装 IDE。IDE 与 SDK 可能共享类似的后端能力，但 SDK 用户只需关心 `localharness` 是否随 wheel 安装成功。

### 常见问题

| 现象 | 原因 |
| :--- | :--- |
| clone 仓库后跑不起来 | 仓库内无 `bin/localharness`，需 `pip install google-antigravity` |
| `Failed to read length from stdout` | 二进制未启动、平台 wheel 不匹配、或 stderr 有崩溃日志 |
| 有 Key 但回复为空 | 早期版本 Harness 在无 Key 时会静默空响应；现 SDK 会在启动前校验 `GEMINI_API_KEY` |
| 源码目录 shadow 了 pip 包 | 在仓库根跑 Python 时，可能 import 到无 bin 的源码树；优先在 venv 里用已安装的包 |

更多安装与验证见 [09_项目运行与功能全景](./09_项目运行与功能全景.md)。
